# 찐친 소리함 ↔ 카카오톡 운영진방 브리지 (검증 전 초안)

## 범위 및 안전 기준
- PR #16 기반 격리 브랜치. 기존 모임/정산/PET/타로/봇 명령어 변경 없음
- **회원은 로그인 닉네임으로만 접수**, 익명 접수 불가
- 접수 전문을 운영진방에 발송하는 정책이므로 해당 방의 **모든 참여자가 전문을 읽을 수 있음**
- 방장·지정 운영진 권한은 명령어 실행 시 **카카오 고유 사용자 ID → profiles.id → 역할/지정 여부**로 재검증
- 카카오닉네임/표시명만으로 인증하지 않으며, ID에 방명이나 채팅 본문을 사용하지 않음
- 답변은 운영진방 확인 메시지와 회원 웹 `내 접수내역`에만 저장/표시하며 일반방에 재전송하지 않음
- **보안 주의:** 고유 ID 매핑 화면에 입력한 값은 실제 봇 이벤트에서 검증한 카카오 사용자 ID이어야 함
- **운영 배포 금지:** 전용 검증 DB 및 봇에 대해 E2E 성공 전까지 실운영에 적용하지 말 것

## 사전 조건
1. PR #16의 `20261126150000_jjinchin_feedback.sql` 적용 후, 본 PR의 `20261126163000_feedback_bot_bridge.sql` 순서로 격리된 Supabase 검증 DB에만 적용
2. Vercel 서버 환경변수:
   - `FEEDBACK_BOT_SECRET`: 충분히 긴 무작위 봇 전용 비밀값. `SUPABASE_SERVICE_ROLE_KEY` 재사용 금지
   - `FEEDBACK_OPERATOR_ROOM_ID`: 실제 운영진방의 변하지 않는 채팅방 식별자
3. 봇 환경변수:
   - `FEEDBACK_API_ORIGIN`: 서버 미리보기 도메인 (검증 완료 후 운영 도메인)
   - `FEEDBACK_BOT_SECRET`: 서버와 일치하는 비밀값
   - `FEEDBACK_OPERATOR_ROOM_ID`: 서버와 일치하는 정확한 운영진방 ID
4. `/feedback`에서 방장이 소리함 담당 운영진을 지정하고, `/feedback/operators`에서 본인과 지정 운영진의 실제 Kakao UID를 연결
5. 운영진방 전체 구성원이 **제보 전문을 열람해도 되는 사람인지** 방장이 확인 후 활성화. 그렇지 않다면 내용전문 알림을 활성화하지 말 것.

## 봇 실제 연결 (현재 자동 적용되지 않음)
`bot-bridge/feedback_helper.py`는 프레임워크에 독립적인 어댑터다. GitHub `main`에는 운영 중인 `irispy.py` 본문이 없고 실제 봇 스크립트는 사이트 봇관리/DB에서 다뤄지므로, 기존 `irispy.py`에 무작정 덮어쓰지 않는다.

현재 실운영 `irispy.py`에서 메시지 핸들러와 기존 주기 스케줄러 인터페이스를 확인한 후:
- 메시지 핸들러 내부에 `feedback_helper.handle_message(room_id, sender_uid, message_id, text, send)`를 기존 명령 라우팅과 충돌하지 않는 위치에 연결
- 기존 스케줄러에 `feedback_helper.pump(room_id, send)`를 **30~60초 간격**으로 추가 (별도 무한 polling 루프 금지)
- 실제 봇 발송 메서드를 `send(room_id,text)` 형태로 래핑
- `room_id`, `sender_uid`, `message_id`는 봇이 신뢰할 수 있는 이벤트 필드에서만 추출
- 명령어 처리 여부(bool)가 True면 기존 핸들러의 다른 명령 처리를 중단하되 다른 명령들은 반드시 원래 동작 유지
- 변경 전후 스크립트 컴파일, 봇 구동, 테스트 운영진방 메시지 송수신 검증 후 `!봇적용`

## 지원 명령어
- `!소리`, `!소리목록`: 미처리 최근 20건
- `!소리 1024`: 내용 전문 조회
- `!답변 1024 답변 내용`: 입력 즉시 비공개 저장, 동일 메시지 ID 재처리 방지
- `!검토 1024`: 검토 중
- `!완료 1024`: 종결
- `!소리내역 1024`: 최근 답변 이력
- `!소리도움`: 사용법

## 메시지 처리 안정성
- 신규 접수의 본문+작성자 연결 완료 후 DB 트리거가 outbox 항목 1건 생성
- `poll`은 PostgreSQL `FOR UPDATE SKIP LOCKED`로 최대 5개 작업 점유
- 전송 성공 후 `ack`로 완료 표시. 실패 시 1/2/4/8/16분 백오프, 5회 실패 시 `failed`
- 봇 장애 후 3분 지난 `sending` 점유 재회수
- 24시간 동안 답변되지 않은 접수 중 최초 발송 완료 건에 한해 **한 번** 재알림
- **중요:** 카카오톡 발송과 DB `ack`은 서로 다른 시스템으로 원자적으로 묶을 수 없다. 발송 직후 연결이 끊기면 동일한 메시지가 다시 올라올 수 있다. 표시된 `발송ID`로 수동 식별 가능하며 정확히 한 번 전송을 보장한다고 주장하지 않는다.
- 답변은 DB의 고유한 `source_message_id` 및 트랜잭션 RPC로 중복 저장 방지
- 회신 이력은 `jjinchin_feedback_reply_history`에 추가 저장하며 기존 최종 답변 스냅샷을 유지
- 발송 실패 5회 최종 오류는 운영자 확인 필요. 자동 무한 재전송하지 않음

## 아직 필요한 운영 연결
이 브랜치는 API/DB/웹 UI 및 **봇 연결 어댑터**까지만 제공한다. 운영 봇은 적용하지 않았으며, 환경변수·실제 카카오 UID·운영진방 ID는 저장소에 넣지 않았다. 운영 봇 스크립트의 최신 본문을 검토해야 irispy.py 연결 부분을 안전하게 마무리할 수 있다.
